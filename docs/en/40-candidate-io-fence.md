# 40. Revocable Candidate filesystem

`agent-computer-fence` adds a trusted Linux FUSE mount in front of one prepared Candidate directory on the existing qualified JuiceFS volume. It provides a mount-local content and namespace drain barrier. The [execution CSI integration](41-fenced-execution-csi.md) now routes actual Pod IO through this mount. Process executions still remain `Unknown`, their writer leases remain `Draining`, and Computer `ready` remains false.

## Why the extra boundary is needed

A workload exiting does not prove that its shared JuiceFS client has finished writing. JuiceFS can retain writer handles and background work after filesystem operations. A control-plane receipt, an empty process cgroup or deletion of a Pod cannot substitute for a storage barrier. The upstream [JuiceFS writer implementation](https://github.com/juicedata/juicefs/blob/v1.4.1/pkg/vfs/writer.go) and [VFS implementation](https://github.com/juicedata/juicefs/blob/v1.4.1/pkg/vfs/vfs.go) describe those paths; [CSI mount sharing](https://juicefs.com/docs/csi/guide/resource-optimization) also prevents treating a shared client as belonging to one Candidate.

The new mount gives the trusted adapter control over every supported modifying request before it enters JuiceFS. All operations use pinned directory/inode descriptors. Tenant names are single components, and resolution rejects path traversal, symlink following and crossing to another filesystem. Only the configured writer UID and trusted root may access the mount, with kernel permission checks retained. JuiceFS operator controls (`.control` and `.jfs.*`) are reserved; its special inode range and foreign-owned backing nodes are rejected. Ordinary tenant `.config` directories remain usable. The [qualified backend internal-node contract](https://github.com/juicedata/juicefs/blob/v1.4.1/pkg/vfs/internal.go) matters because `.control` is exposed below subdirectories too.

## Seal and persistence contract

Every content or namespace mutation holds the mount's operation lock and completes the backing operation and required file/directory synchronization before its FUSE reply. Writes use a writable backing descriptor, including writes to unlinked files. Creating files establishes ownership and permissions before acknowledgement. Compound metadata operations synchronize partial changes even if a later field fails. Ambiguous storage failures permanently prevent a positive drain receipt.

`MountedFence::seal()` first closes the gate irreversibly, then acquires that same operation lock. An operation already admitted must finish before seal can succeed. Queued and future mutations receive `EROFS`, including writes through descriptors opened before sealing and descriptors whose names have been unlinked. A stalled backing client stalls seal; no timeout is converted into success. Reads remain available. Incidental access-time metadata from reading is outside this content/namespace barrier.

The returned opaque `SealedFence` binds the prepared-directory identity, random mount instance and accepted request count. Its JSON `Evidence` is audit metadata; JSON cannot reconstruct a live proof. Status flags are diagnostic observations and do not certify drain. Unmounting or losing the process is not a successful seal.

The pinned `fuser` dependency uses direct I/O and does not negotiate writeback caching, passthrough, DAX or shared writable mmap. This first component supports regular files, directories, read/write, truncate, permissions, timestamps, rename and removal. Symlinks, hardlinks, devices, extended attributes and shared writable mmap are unavailable. There are limits of 16,384 retained inode identities, 4,096 open handles and 128 KiB per read/write request. Inode identities remain pinned for the mount lifetime. Directory quota enforcement remains in JuiceFS; `statfs` reports backing availability capped by the Candidate's quota, not an independent quota reservation.

## Trusted integration boundary

The operator opens the existing qualified `MountedVolume`, obtains `candidate_directory(&prepared)`, and passes that verified handle to `agent_computer_fence::mount`. The mountpoint must be empty, absolute, owned by root, and reached only through root-owned ancestors that are not group/world writable. The backing descriptor and path must remain inaccessible to workloads. Only this FUSE mount may be exposed to a workload with exclusive writer admission. Sealing one mount does not revoke another mount of the same directory, legacy direct CSI access, or writes made directly by trusted code.

The original filesystem component did not introduce a public mount endpoint or database completion transition. Section 41 adds private node publication and execution/Pod binding. Combining the live IO proof with process fencing and accepted completion remains outstanding. Successful sealing alone does not authorize a new writer or claim that network/process effects have ended. Unsupported filesystem operations must be resolved before general application compatibility can be claimed.

## Verification

Six focused unit tests cover joining in-flight I/O, old and unlinked handles, real synchronization errors, path/link/mode rejection, ordinary namespace errors and pinned inodes across path replacement. The full default Cargo and Bazel suites, Clippy, formatting, documentation validation and existing Qualitygate policy are recorded separately in the [delivery evidence](../evidence/candidate-io-fence-2026-10-10.json) and [logs](../evidence/candidate-io-fence-2026-10-10.log).

The explicit `candidate_worker_live_test` fixture uses real K3s/CSI, PostgreSQL, JuiceFS and S3. Add `fence_mount_root` to its private configuration, pointing to an existing root-owned directory such as `/var/lib/agent-computer-fence`. Run as root in a disposable VM with FUSE and `/usr/bin/setpriv`. Its workload drops to UID/GID 1000 with no supplementary groups, creates and modifies files through the new mount, holds linked and unlinked descriptors, and confirms shared writable mmap is rejected. The fixture first establishes that JuiceFS exposes its special control inode under the backing Candidate, then rejects both control names through the gateway at two directory depths while allowing ordinary tenant `.config/settings`. The operator then pauses the specific native JuiceFS client, observes an active mutation, and verifies seal cannot complete for 300 ms. After resuming the client, seal succeeds and ten modifying operations are rejected while reads retain the correct bytes. The operator also verifies the backing bytes. A separate read-only JuiceFS process with its data cache disabled independently reads the same seven bytes after sealing.

This is single-VM component evidence. It does not establish crash/power-loss recovery, HA, product Pod integration, general process fencing or complete Computer acceptance. T01–T43 remain `not_run`.
