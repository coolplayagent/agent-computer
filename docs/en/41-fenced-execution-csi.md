# 41. Fenced execution mounts through CSI

The single-execution worker now publishes the [Candidate FUSE boundary](40-candidate-io-fence.md) to actual gVisor Pods. Production dispatch uses an inline `csi.agent-computer.io` volume and verifies the front filesystem before issuing a startup grant. The workload namespace remains under PodSecurity `restricted`; the Pod receives neither a hostPath nor the backing JuiceFS directory.

Execution completion is still conservative: `Unknown` executions and `Draining` writer leases remain unresolved. This integration does not combine process termination, durable output and the live IO barrier into an accepted completion transaction. Computer `ready` remains false and T01–T43 remain `not_run`.

## Publication and startup

After committed dispatch and local preparation/quota verification, the worker creates a fresh private mountpoint for the execution under `/var/lib/agent-computer-csi/mounts`. Mountpoints are never reused. A reference records the random mount instance, complete preparation receipt, device/inode, boot ID and mount namespace. Deserializing this reference cannot reconstruct a live `MountedFence` or `SealedFence`.

The Pod journal binds this reference and the exact Node name/UID/boot to the admitted execution. Before its one Pod create attempt, the worker durably registers the live mount and intended Pod name/namespace/node in the root-only local registry. The CSI publisher accepts only the Kubelet's expected ephemeral context, service account, mount capability and exact workspace target path. Its first publication durably claims the instance for one Pod UID, CSI volume ID and target. Another UID, volume or target is rejected even when the Pod name is unchanged.

Publication clones the pinned FUSE tree with `open_tree` and attaches it to a pinned target with `move_mount`. The resulting mount must have the recorded device, root, instance-specific source and qualified `fuse` type. It is made private before and after attachment because attachment beneath a shared host parent can create a new peer group. Exact retries observe the existing mount without stacking or replacing it. Registrations, claims and revocation tombstones use bounded root-owned files, synchronization and a shared nonblocking lock. Partial or malformed records fail closed; there is no automatic state garbage collection.

Before command authorization, the node adapter independently checks the actual container runtime workspace source against the inline CSI target and checks its device/root inode against the live FUSE handle. The watchdog registration transaction requires that observation to match the Pod journal and admitted preparation. Existing Pod/Node UID, runtime, cgroup, dual watchdog and reaper checks remain required. The legacy direct-Candidate compiler is retained for historical cleanup/component fixtures; the dispatch command has no direct-mount fallback.

## Exit, loss and recovery

On every return from the dispatch attempt, the controller immediately closes the mutation gate. It lowers database authority, records local publication revocation, requests conditional Pod deletion, persists bounded output when available and attempts a seal. Only successful seal returns `io_fence` audit metadata. A timeout, detached mount, empty cgroup, process report or stored reference cannot manufacture that result or release the writer lease.

Controller death disconnects its FUSE connection: new writes through already-open descriptors fail. An operation submitted to the backing filesystem before death may still be unresolved, so this is not a successful drain. The independent watchdogs/reaper still handle surviving processes. Recovery reconstructs the exact recorded Pod plan for cleanup, revokes future publication and observes journals; it never recreates the mount, reissues a grant or supplies an IO seal.

CSI unpublish persists revocation before detaching. It validates the recorded target and mount identity without requiring the dead FUSE source to answer filesystem calls. Repeated cleanup of an absent target succeeds. A foreign/replaced mount is retained and reported as a failed precondition. Publisher restart retains durable claims and cannot reopen a revoked instance.

## Operator deployment

Build `//crates/csi:agent-computer-csi` and install the binary as a trusted root-owned node executable. Install an operator-verified upstream [node-driver-registrar](https://github.com/kubernetes-csi/node-driver-registrar/tree/v2.9.0) executable at `/usr/local/bin/csi-node-driver-registrar`. The component record pins the tested registrar image and extracted binary checksum. The registrar handles Kubelet plugin registration; the Rust service handles CSI Identity and Node RPCs. Kubelet's registration client uses a socket-path authority that the strict Rust HTTP/2 stack rejects, while its CSI client explicitly uses `localhost`; using the upstream registrar preserves standard protocol handling. See the [registration client](https://github.com/kubernetes/kubernetes/blob/master/pkg/kubelet/pluginmanager/operationexecutor/operation_generator.go) and [CSI client](https://github.com/kubernetes/kubernetes/blob/master/pkg/volume/csi/csi_client.go).

Install [the publisher unit](../../deploy/agent-computer-csi.service) and [registrar unit](../../deploy/agent-computer-csi-registrar.service), create a root-owned `/etc/agent-computer/csi.env` containing the exact `NODE_NAME`, and apply [the CSIDriver declaration](../../deploy/candidate-csi.yaml). Match the units' K3s dependency to the actual operator service name, then enable/start `agent-computer-csi.service`. Confirm the driver appears in the node's `CSINode` record before dispatching. The units create the private registry and plugin socket directory; state must remain on durable local storage across publisher restarts.

The publisher, native qualified JuiceFS mount and execution controller must share the host mount namespace. Do not add systemd filesystem isolation that silently creates another mount namespace. The CSI socket is root-only, checks peer UID and has no TCP listener. The upstream registrar also exposes no HTTP listener with these arguments. No Controller, Stage, Expand, block-volume, custom filesystem, custom mount option or volume-mount-group capability is offered. Filesystem operation limits from section 40 still apply. Backing directories, privileged node processes and registry files remain operator-only.

## Verification and limits

The [component record](../evidence/fenced-execution-csi-2026-10-10.json) and [logs](../evidence/fenced-execution-csi-2026-10-10.log) bind the tested source and executables. Default tests cover context/capability rejection, direct-mount substitution, Node identity and cleanup mount identity. The explicit `execution_worker_live_test` runs eleven real PostgreSQL/K3s/gVisor/JuiceFS/S3 scenarios. Its private config must additionally set `csi_test_binary` to the built `//crates/csi:csi_live_test` executable. During cancellation it invokes the exact active execution test, proving retry, replacement-UID rejection and publisher restart preserve the mounted instance. Controller-kill tests verify an old FD rejects writes while stopped PID 1 still needs the independent timer.

After that fixture, run `csi_live_test --exact real_csi_cleanup_replay_and_peer_boundary --nocapture` with `AGENT_COMPUTER_CSI_DISPOSABLE_TEST=1` and `AGENT_COMPUTER_CSI_TEST_INSTANCE` set to the completed normal execution's instance. It exercises real Unix gRPC, repeated cleanup, revoked replay, wrong identities, a deliberately replaced foreign bind mount and a UID/GID 1000 client with no supplementary groups. Run only in an explicitly disposable host environment. Independent fresh-client JuiceFS and signed S3 reads are separate evidence from the controller's reports.

This is single-node component qualification, not multi-node fencing, power-loss recovery, a general application filesystem or complete Computer acceptance. Registry retention/reclamation and accepted execution completion still require further work.
