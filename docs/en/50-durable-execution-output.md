# 50. Durable execution output chunks

New admissions enable `stream_output` by default. The trusted supervisor publishes retained stdout/stderr while the command is running. Clients can poll a verified sequence cursor, download binary chunks, and resume reading after disconnect without dispatching the command again. This is the bounded Candidate execution path; it does not enable public Computer execution.

## Policy and transport

An omitted input remains omitted in its canonical bytes. Only a new admission adds `output_stream: {version: 1}` to its immutable binding. Migration 30 does not enable streaming for historical records, including queued requests. Explicit false retains protocol v1 for fixed execution or v2 for renewable execution. Omitted, true and false remain different retry inputs. Returned `stream_output` describes this admitted policy.

Protocol v3 has separate bootstrap, challenge and startup-grant hash domains. Streaming and renewal are independent: v3 without a hard budget uses the original fixed deadline; v3 with a hard budget uses the existing dual-guard renewal protocol. V1/v2 bytes and digests remain compatible.

A chunk carries a startup-grant digest, shared sequence, previous chunk digest, stream name, stream offset, observed byte count, truncation and EOF. Each payload is at most 8192 bytes; serialized frames are bounded to 40 KiB and an execution accepts at most 8192 chunks. Each stream retains at most its admitted cap (maximum 1 MiB); excess bytes are drained and counted. Full chunks are emitted promptly, partial chunks at approximately one-second intervals, and EOF closes each stream. A capped stream does not emit unlimited empty progress frames.

The supervisor uses nonblocking IO and one pending frame. Renewal challenges take priority between frames, with the original pre-emission deadline anchor. Attach validates identity, sequence, per-stream offsets, hashes and EOF before producing an opaque observation. Cancelled reads preserve partial frames. Coalesced output and renewal frames share transport but keep separate digest chains. The final report must match every delivered byte and its exact stream progress; success requires both complete EOF prefixes. An outstanding renewal challenge must receive its grant before a normal final report, including when the command has already exited and output reaches EOF. Waiting never extends the existing deadline.

## Persistence and interruption

The worker has one serial publisher, eight queued chunks and one active publication. Private spool writes use at most four blocking workers across publishers; cancellation cannot release a slot while its blocking work still runs. A full queue pauses attach reads while authority and deadline checks continue. Storage pressure can interrupt execution; it cannot extend its lease. A supervisor can exit before its buffered final report reaches the worker. If health checks then stop reporting a live guard, the worker may continue receiving only after the original pinned cgroup and every original runtime pidfd prove termination. It immediately closes Candidate IO, grants no more renewals, and keeps the existing authority/deadline checks. Accepted completion still requires the later live IO seal.

Each chunk first gets an immutable database intent and Outbox event bound to the original dispatch, Pod, startup and watchdog arm. Bytes go to a private spool and a fixed content-addressed object, whose signed read-back must verify before the acknowledgement and Outbox commit together. PostgreSQL stores references and counts, never stdout/stderr bytes. Only a contiguous acknowledged prefix is visible. No chunk may follow stream EOF or a recorded final report.

`execution-output-chunks-recover --database-url-file PATH --organization ID --execution-id ID --config-file PATH` retries the one pending publication using its original manifest and spool/object identity. It needs no Kubernetes credentials and returns `recovered_chunk` or null. It does not reconstruct an attach channel or restart, renew or complete the execution. If neither the fixed object nor the original spool contains the pending bytes, recovery remains unavailable. Controller death can lose buffered, unrecorded chunks; already verified chunks remain readable. A readable prefix, EOF, or verified final report is not accepted execution success.

## HTTP reads

- `GET /v1alpha1/executions/{id}/output-chunks?after_sequence=0&limit=16` returns metadata for at most 32 chunks. `next_sequence` is the resume cursor; `available_sequence` describes the verified prefix. `execution_state`, `final_sequence` and `final_report_verified` separately describe execution and final-report observations. An empty page does not imply completion. Metadata works without an output gateway.
- `GET /v1alpha1/executions/{id}/output-chunks/{sequence}` returns exactly one verified binary chunk, including a zero-byte EOF chunk. Headers bind its sequence, stream, offset, SHA-256 and chunk digest. Chunk and final-output downloads share four slots, retained until the response body is consumed or dropped.
- Existing `/output/{stdout|stderr}` returns the retained final stream. It does not provide a live cursor.

Reads require the original valid credential with `runtime.connect` and `runtime.read`, current Computer connect/read and original Workspace read grants. Download authorization runs before and after object IO, including failed GET. Closing the logical connection or losing modify authority does not remove historical read access. Each read verifies object size/hash and the wire digest; no object URL, key, supervisor report or credential is exposed. Unknown/duplicate/empty queries, invalid bounds and Range requests are rejected. Metadata pages and binary bodies use no-store/nosniff responses.
